# Milestone 4 — Tradeoffs & Remaining Risks

Scope: changes after `aa26e8a` (M4 features, Sepolia deployment/verification, security tests,
configuration warnings, RPC-call reduction). Format follows Section 4 of the M4 template.

## A. Tradeoffs made to reach feature-complete

| Tradeoff | Impact if unresolved | Mitigation plan |
| --- | --- | --- |
| **Immutable contracts, no proxy/admin.** Adding `isRecoveryTargetCurrent` required a full redeploy (new Sepolia factory `0xb8A3…` replaced `0x2B41…`); M3 wallets cannot get the new view. | Any contract bug found in M5 testing means redeploying and moving test funds; wallets on the old factory become orphaned and the UI cannot show Invalidated status for them. | Keep redeploys rare and only when Solidity changes. `verify:deployment` blocks Pages publishing when on-chain bytecode differs from the build. Document the migration step (create a new wallet, propose a payment of the full balance to it) in the final user guide. |
| **"Invalidated" is a UI-only label, not a Solidity status.** The service derives it from `isRecoveryTargetCurrent`. On-chain the request stays Pending/Queued until it is cancelled or expires. | Block explorers and other clients still show the request as active. The replacement address stays reserved until expiry (24h on Sepolia), so it cannot be used in a new recovery until then. | The UI keeps cancellation available and explains why. Execution is safe because the contract still reverts with `NotOwner`. Document "cancel or wait for expiry before reusing the address" (already in ARCHITECTURE.md). |
| **Low thresholds are warned about, not forbidden.** M=1, K=1, M=N and K=G are still valid (M3 feedback suggested minimum constraints *or* warnings). | A one-owner or one-guardian wallet can be created or reached through governance, which removes the multi-party protection the project exists to provide. The warnings appear only in our frontend. | This keeps the frozen spec's accepted configurations. Warnings appear on creation, overview, governance previews and recovery. Tests: `safety.test.mjs` and browser checks. If graders want an enforced minimum, adding one is a single validation change in the contract and `validateConfig`, plus a redeploy. |
| **Queued requests keep their original `readyAt`.** Restoring a lost quorum does not restart the timelock, and raising delays does not apply to items already queued. | Suppose a queued payment loses quorum (an owner is removed) and the delay has already passed. One new approval then makes it executable **immediately**, with no fresh monitoring window for the other owners. A delay increase also does not protect items already in the queue. | This choice is documented in ARCHITECTURE.md (it answers the M3 feedback question) and tested in T30 and the M4 governance scenario. Owners can still use cancellation (N−M+1 votes) as a veto. Consider listing this in the known-issues section as a deliberate choice rather than a guarantee. |
| **Queueing is event-driven.** Lowering M does not queue Pending items that now have enough approvals; another approval has to trigger it, and the timelock starts then. | The UI can show "2/2 approvals" while Execute is disabled, which is confusing in a demo. Safe: it only adds delay. | Documented in ARCHITECTURE.md. An owner who has not approved yet can approve, or an approver can revoke and re-approve. |
| **Wallet discovery scans `WalletCreated` logs** instead of changing the factory or adding an indexer. | Wallets from other factories must be added by address. Discovery state is held in memory, so each page load rescans once from the factory's deployment block. | Works in fresh browsers with no contract change. Scans are now incremental after the first (see R2). Production use would need an indexer (e.g. The Graph), which stays out of scope. |
| **Manual Sepolia deploy, automated read-only verification.** CI holds no deployer key. | Deployment depends on one team member's machine and key. A forgotten commit of `deployments/11155111.json` or `public/…` leaves the hosted site stale. Pages skips publishing when no record exists. | DECISIONS.md explains the choice. `deploy.mjs` prints the commit reminder and runs Etherscan verification. `verify:deployment` gates every Pages publish. |
| **Public fallback RPC (`publicnode.com`)** when `VITE_RPC_URL` is empty. | Every read the UI shows (balances, statuses, previews) comes from a third-party node we do not control. The node may rate-limit, lag behind, or return wrong data. MetaMask signs transactions, but users decide based on what the UI displays. Its load balancer also mixes nodes that are a block apart (see R10). | Acceptable for test funds only. Set an origin-restricted `VITE_RPC_URL` repository variable for the hosted build. Note this in the trust-assumptions section. |
| **Fewer RPC calls** (commit `e90ca85`): `staticNetwork`, one cached chain-ID check, removed the per-wallet log subscription, 30s heartbeat (previously 5s), 4s polling on Sepolia. | Refreshes now rely only on block polling, focus and the 30s fallback. If block polling stalls, the UI can be up to about 30s stale. The cached chain ID is never re-checked if the RPC endpoint switches networks. | Wallet events always arrive in a new block, so the block trigger is sufficient. The heartbeat and focus refresh cover stalls. A test starts a fresh service after external changes with no subscription. A real RPC outage or reconnect is still untested (see R4). |

## B. Remaining risks heading into M5 testing and integration

| # | Risk | Impact if unresolved | Mitigation plan |
| --- | --- | --- | --- |
| R1 | **Not externally audited. Security tests check our stated invariants and do not fuzz governance or recovery.** The fast-check test (T29) covers payment sequences only (seed 416, 6 runs). | An unknown interaction between governance, recovery and generations could break M-of-N or let a stale request execute, and the funds involved can be moved. | In M5, extend fast-check to random sequences of governance and recovery actions, with invariants for live-vote counts, generation, and "an executed recovery targets the current owner". Run Slither, and add a coverage report (`solidity-coverage` or an equivalent), since M3 feedback asked for coverage numbers. |
| R2 | **RPC load growing with chain age (mitigated).** `listWallets` used to rescan all factory logs after every confirmed transaction, and the Activity tab rescanned the wallet's whole history on every block. | Before the fix, public-RPC calls grew by about 4 `getLogs` per day of deployment age per scan, causing slow loads and rate-limit errors. | Fixed: scans are incremental. Only new blocks are fetched, plus the last 5 re-read in case of a reorg. Deployment blocks are cached, and membership checks run in parallel. Measured against live Sepolia, repeat discovery took 0.5s (first 1.4s) and repeat history 0.35s (first 1.7s). Remaining: the first scan on each page load still starts at deployment, and per-block refresh reads grow with the number of proposals. A cache that persists across page loads or an indexer would be future work. |
| R3 | **No testing with the real MetaMask extension.** All browser tests use an injected EIP-1193 adapter. The new `wallet_switchEthereumChain`/`wallet_addEthereumChain` flow and the `chainChanged` change that keeps the account connected have only been tested with mocks. | The demo could fail on MetaMask-specific behaviour: error code 4902 nested in `originalError`, pending-permission errors, or account or chain race conditions. `addEthereumChain` also writes `config.rpcUrl` into users' MetaMask. That URL could be a keyed RPC URL, or `localhost` for chain 1337. | Run the manual grading checklist in TEST_PLAN.md (3 owners, 2 guardians) with real MetaMask on Sepolia, using fresh accounts. Record the results in M5. |
| R4 | **Real-network timing and gas are unmeasured.** Sepolia uses demo delays (15s/60s/120s/180s), close to the 12s block time. | Timelock boundaries that tests confirm on Ganache can be off by a block on Sepolia, so a "Ready" status may still revert with `TimelockActive`. Gas costs for governance and recovery are unknown. | Record gas and confirmation times for each action during the M5 Sepolia run. The UI already shows Ready only when chain time ≥ `readyAt`, and the contract rechecks. Consider a small buffer or a hint in the demo script. |
| R5 | **Trust assumptions in recovery** (from M3 feedback): guardians are honest; a stolen key of the targeted owner can veto recovery; there is no bypass when both the owner quorum and the guardian quorum are lost. If M=N, other owners cannot veto a recovery either. | A wallet can become permanently stuck, or a compromised key can block its own replacement. Both are by design, but they can be mistaken for bugs. | These are disclosed in the UI warnings, ARCHITECTURE.md and SECURITY_SCENARIOS_M4.md. Covered by tests: guardian collusion, target veto, unavailable guardian, lost owner quorum. Keep them listed in the known-issues section. |
| R6 | **Authorized collusion is out of scope.** A quorum of M owners can move funds up to the caps and rewrite policy. | Caps and delays limit damage only while honest owners watch and cancel within the window. | State this as an explicit assumption. Monitoring or alerts are future work. |
| R7 | **CI and hosting evidence missing.** CI runs lint, tests, build, an ABI-drift check and the browser tests, but there is no branch protection and no record of a hosted run. Pages runs the Etherscan check only when `ETHERSCAN_API_KEY` is set. Without the key the check is skipped and the publish still succeeds. | The M3 feedback ("enforce the actual CI gates") is still only partly addressed. An unverified source could be published without anyone noticing. | Enable branch protection that requires `CI / verify`. Add the `ETHERSCAN_API_KEY` secret and consider failing the job instead of skipping. Link the successful Actions runs in the submission. |
| R8 | **The mock service diverges from the EVM.** The mock marks invalidation when a member is removed, while the chain uses generation comparison. | The mock-mode demo can show different results from Sepolia in edge cases, such as removal followed by re-adding. | The mock is labeled "simulated". Use the real local chain or Sepolia for security demos. |
| R9 | **Documentation drift.** PROTOTYPE_STATUS.md still says the app "has not been deployed to Sepolia", although `deployments/11155111.json` exists. Docs refer to a "demo ZIP" and "PR #9". Test counts differ between files (34, 43, 66). The M4 template's test table only fills T1–T31. | Graders lose confidence when the docs contradict the repository. Placeholder rows T32–T77 marked "Passing" would overstate coverage. | Update PROTOTYPE_STATUS.md. Remove the ZIP and PR #9 references. Add the 35 newer tests (9 adversarial, 5 warning/preview, 10 service, 8 explorer, plus the M4 contract regressions) to the template as T32–T66 and delete the unused placeholder rows. |
| R10 | **Lagging nodes behind the public RPC (mitigated).** The hosted site failed to load with `block not found` / `header not found` (-32001/-32000). The app reads the newest block number, then pins dozens of reads to it, and the load balancer routes some of those reads to nodes that haven't imported that block yet. Reproduced at about 1 in 40 reads at the newest block, versus 0 in 40 two blocks back. Each refresh makes dozens of pinned reads, so many refreshes failed. | Data intermittently failed to load on the hosted site. | Fixed: `src/services/rpcRetry.js` retries only missing-block errors, up to 4 attempts with backoff, on the provider the app creates. Verified with 25 of 25 full refreshes against live Sepolia and unit tests in `test/rpcRetry.test.mjs`. A dedicated RPC via `VITE_RPC_URL` would make this rarer still. |
| R11 | **Cancel majority does not block execution (deployed contracts).** `execute()` does not check cancel votes. If M is raised or an owner is removed, the cancel threshold can fall to or below the votes already cast. If every remaining owner has already voted, no one can cast the vote that finalizes the cancellation. Example: 3 owners, M=1, A and B vote to cancel, C is removed. | A veto that has a majority under the current rules can still be overridden: any owner meeting M can execute the payment. | Documented in ARCHITECTURE.md. The fix is one check in `execute`/`executeRecovery`. It changes the bytecode, so `verify:deployment` would block Pages publishing until a Sepolia redeploy; it is deferred to the next redeploy. Until then, owners should vote to cancel before any membership or threshold change executes. Add a regression test with the fix. |
